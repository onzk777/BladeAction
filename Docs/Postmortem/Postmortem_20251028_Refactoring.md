## ✅ 잘한 점 (What Went Well)

### 1. 체계적인 네이밍 통일
- **문제 인식**: "Effective", "Map" 등 혼란스러운 네이밍
- **해결**: "Final", "Convert"로 일관되게 변경
- **효과**: 코드 가독성 향상, 향후 유지보수 용이

**배운 점**: 초기 네이밍이 중요하다. 나중에 바꾸려면 대규모 리팩토링 필요.

---

### 2. Deprecated 필드 과감한 제거
- **문제**: 15개 이상의 deprecated 필드가 계속 발목을 잡음
- **결정**: 마이그레이션 도구 제거하고 deprecated 필드도 완전 삭제
- **효과**: 코드베이스 깔끔, 경고 0개, 혼란 제거

**배운 점**: Deprecated는 임시 수단. 일정 기간 후 과감히 제거해야 기술 부채 방지.

---

### 3. 구조 단순화 (InventoryUI 참조 방식)
- **문제**: InventoryUI가 Inventory를 "소유"하여 Scene 파일에 저장됨
- **해결**: Character 참조 방식으로 변경, Inventory는 간접 접근
- **효과**: Scene 파일 오염 방지, 확장성 확보

**배운 점**: Unity의 SerializeField는 편리하지만 런타임 전용 데이터에는 사용 금지.

---

### 4. 자동화 시스템 구축
- **구현**: CharacterManager가 Inventory 자동 생성/초기화
- **효과**: 수동 설정 불필요, 휴먼 에러 방지
- **확장**: CharacterData의 initialItems/initialEquipment로 선언적 정의

**배운 점**: 자동화는 초기 투자가 크지만 장기적으로 생산성 향상.

---

### 5. 체계적인 테스트 인프라
- **StatsTest.cs**: 9개의 독립적 테스트 케이스
- **리팩토링_테스트_케이스.md**: 절차 중심 검증 가이드
- **효과**: 회귀 테스트 용이, 문제 조기 발견

**배운 점**: 테스트 코드를 먼저 작성하면 구현 품질 향상.

---

### 2. RecalculateAndCommit() 버그 늦은 발견
**문제:**
- `character.stats = finalStats;` 누락
- HP 비율 보존 기능이 작동 안 했는데 뒤늦게 발견

**원인:**
- 테스트 케이스를 먼저 작성하지 않음
- 코드 리뷰 부재

**교훈:**
- 핵심 로직은 반드시 테스트 먼저 작성 (TDD)
- "커밋"이라는 이름이 붙으면 실제로 데이터를 저장하는지 검증 필수

**개선안:**
- 다음부터는 테스트 케이스 먼저 작성 → 구현 → 검증 순서

---

### 3. InventoryUI 초기화 타이밍 이슈
**문제:**
- InventoryUI.Start()가 CharacterManager.Awake()보다 먼저 실행
- PlayerCharacter가 아직 없는 상태에서 연결 시도
- InventoryTestManager와 충돌

**원인:**
- Unity 생명주기 실행 순서를 고려하지 않음
- Scene에 여러 초기화 주체가 존재 (CharacterManager, InventoryTestManager, InventoryUI)

**교훈:**
- Unity의 Awake/Start 순서는 보장되지 않음
- 의존성이 있는 초기화는 반드시 지연 초기화 또는 명시적 순서 제어

**개선안:**
- Script Execution Order 설정 또는
- 코루틴 지연 초기화 (현재 채택)
- 또는 중앙 초기화 매니저 패턴 도입

---

### 4. 테스트 케이스 문서 혼란
**문제:**
- 처음에 "테스트 케이스"에 코드 스니펫을 넣음
- "구현 지시서인가 검증 절차서인가" 혼란
- 사용자의 지적으로 수정

**원인:**
- 문서 목적을 명확히 정의하지 않음
- "테스트 케이스"의 의미를 잘못 이해

**교훈:**
- 문서는 목적을 명확히 (구현 가이드 vs 테스트 절차)
- 코드는 실제 파일로, 문서는 절차/체크리스트로
- 독자가 "무엇을 해야 하는가"를 명확히 알 수 있어야 함

**개선안:**
- 문서 상단에 "이 문서의 목적" 섹션 필수
- 체크리스트 형식 선호
- 코드 예시는 최소화

---

### 5. Input Actions 파일 직접 수정 시도
**문제:**
- JSON 형식의 .inputactions 파일을 코드로 직접 수정 시도
- 사용자가 "직접 수정하지 마라" 지적
- 변경사항 revert됨

**원인:**
- Unity Input System의 워크플로우 이해 부족
- "에디터에서 설정하는 것"과 "코드로 생성하는 것" 구분 실패

**교훈:**
- Unity 에셋 파일(.asset, .inputactions 등)은 에디터에서만 수정
- 코드로 수정하면 동기화 문제 발생 가능
- 사용자 워크플로우 존중 필수

**개선안:**
- Unity 에셋 수정 전 반드시 확인 요청
- 가이드만 제공하고 직접 수정은 사용자에게 맡김

## 🎓 기술적 학습 (Lessons Learned)

### 1. Unity Input System
```
✅ 배운 것:
- Action Map은 여러 개 동시 활성화 가능
- UI 맵은 항상 활성화 유지
- Behavior 설정: "Send Messages" vs "Invoke Unity Events"

❌ 실수:
- .inputactions 파일을 코드로 수정 시도
```

---

### 2. C# Struct vs Class
```
✅ 이해:
- CombatStats는 struct → = 연산자가 값 복사
- CharacterInventory는 class → 참조 전달
- character.stats = finalStats; 는 전체 필드 복사

⚠️ 주의:
- Struct 복사는 비용이 있지만 안전
- Class 참조는 빠르지만 의도치 않은 수정 위험
```

---

### 3. Unity 생명주기의 함정
```
❌ 가정 (틀림):
- Awake는 항상 Start보다 먼저 실행
- 같은 Scene의 모든 Awake가 먼저, 그 다음 모든 Start

✅ 실제:
- GameObject A의 Awake → Start
- GameObject B의 Awake → Start
- 순서는 비결정적!

💡 해결:
- 지연 초기화 (코루틴)
- Script Execution Order
- 명시적 초기화 호출
```

---

### 4. 데이터 격리의 중요성
```
CharacterData (ScriptableObject) - 템플릿
  ↓ 복사
Character.stats (런타임 인스턴스) - 변경 가능
  ↓ 격리
CharacterData는 절대 수정 안 됨 ✅

중요: Inventory 변경이 CharacterData에 영향 주면 안 됨!
```

## 💡 설계 결정 회고

### 결정 1: Combatant → Character (✅ 좋은 결정)
**맥락**: Combatant는 전투만, Character는 더 넓은 의미

**대안 고려:**
- Actor 도입 (상위 개념)
- 현재 구조 유지

**선택**: Character로 변경, Actor는 보류

**결과**: 
- ✅ 의미가 명확해짐
- ✅ 확장성 확보 (비전투 NPC 추가 시 Actor 도입 가능)

**회고**: 올바른 결정. 하지만 초기에 했으면 더 좋았을 것.

---

### 결정 2: InventoryUI의 Character 참조 방식 (✅ 좋은 결정)
**맥락**: InventoryUI가 Inventory를 직접 소유 vs 간접 참조

**대안 고려:**
- Inventory 직접 소유 (기존)
- Character 참조, Inventory 간접 접근 (변경)

**선택**: Character 참조 방식

**결과**:
- ✅ Scene 파일 오염 방지
- ✅ 런타임 격리 보장
- ✅ 확장성 (다른 Character의 Inventory도 표시 가능)

**회고**: 완벽한 결정. 사용자의 지적("왜 Inventory를 가지고 있냐")이 핵심을 찌름.

---

### 결정 3: Deprecated 필드 완전 제거 vs 유지 (✅ 좋은 결정)
**맥락**: 하위 호환 vs 깔끔한 코드베이스

**대안 고려:**
- Deprecated 유지 + 마이그레이션 도구
- 완전 제거

**선택**: 완전 제거

**결과**:
- ✅ 경고 0개
- ✅ 코드 가독성 향상
- ⚠️ 기존 CharacterData 에셋이 데이터 손실 가능성

**회고**: 올바른 결정이지만, 프로덕션에서는 마이그레이션 스크립트 1회 실행 후 제거가 안전.

---

### 결정 4: Input Actions 파일 직접 수정 시도 (❌ 나쁜 결정)
**맥락**: B 키 바인딩 추가 필요
